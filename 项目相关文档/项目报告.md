## 1. 项目背景

### 1.1 项目概述

RemindMe（Life Reminder）是一个基于 AI 大模型的智能提醒管理系统，旨在通过自然语言对话、课表自动导入等方式帮助用户高效管理日常提醒事项。系统集成了通义千问（Qwen）大语言模型，支持 ReAct（思考-行动-观察）模式的智能体调度，能够理解用户意图并自动调用工具完成提醒创建、天气查询等操作。

### 1.2 开发背景

传统提醒应用存在以下痛点：
- **输入繁琐**：用户需要手动填写标题、时间、地点等字段，操作步骤多
- **课表管理低效**：学生用户每学期初需要手动录入大量课程提醒，重复劳动
- **冲突感知弱**：多个提醒时间重叠时缺乏智能检测和处理机制
- **交互单一**：仅支持表单输入，不支持自然语言对话

RemindMe 针对以上痛点，提供以下核心能力：
- **自然语言创建提醒**：用户说"明天下午3点提醒我开会"，系统通过 DeepSeek 大模型自动解析并创建
- **Excel 课表一键导入**：上传课表文件，通义千问大模型自动识别课程信息并批量生成提醒
- **智能冲突检测**：创建提醒时自动检测时间冲突，通过卡片交互让用户选择处理方式
- **实时 WebSocket 推送**：确认卡片、导入结果等通过 WebSocket 实时推送到前端
- **RAG 长期记忆**：基于 Chroma 向量数据库，实现用户私有记忆存储和检索，支持"记住我的偏好"
- **多模型协同**：DeepSeek 负责对话推理与工具调用，通义千问负责课表结构化识别，各取所长

## 2. 需求分析

### 2.1 功能需求

#### 2.1.1 AI 智能对话

- 用户通过自然语言与系统对话
- 系统自动识别用户意图（创建提醒、查询天气、闲聊等）
- 支持多轮对话上下文记忆
- 支持工具调用（Tool Calling）：创建提醒、查询天气、查询日历等
- 条件逻辑处理："如果明天下雨就提醒我带伞"

#### 2.1.2 提醒管理

- 创建提醒：支持自然语言创建和表单创建
- 时间段提醒：支持开始时间和结束时间（如"8点到10点"）
- 循环提醒：支持每日、每周、每月重复
- 冲突检测：创建时自动检测时间冲突
- 确认会话：待确认状态的提醒需要用户确认后生效
- 优先级管理：LOW / NORMAL / HIGH

#### 2.1.3 课表导入

- Excel 文件上传与解析
- AI 自动识别课表结构（课程名、教师、教室、周次、节次）
- 时间配置：用户可调整每节课的开始/结束时间
- 学期配置：设置学期开始日期和总周数
- 时间联动：修改一节课时间后自动推算后续课程时间
- 批量创建：静默创建所有日程，避免消息轰炸
- 手动创建：用户可手动输入课程信息

#### 2.1.4 冲突处理

- 冲突检测算法：单点提醒（±30分钟）和时间段提醒（区间重叠）
- 冲突卡片推送：通过 WebSocket 推送到 `/queue/confirmations`
- 用户操作选项：确认创建、覆盖（删除冲突提醒）、修改时间、取消
- 批量覆盖：支持勾选多个冲突提醒进行批量覆盖
- 卡片状态恢复：取消修改时恢复原始卡片数据

#### 2.1.5 天气服务

- 实时天气查询：和风天气 API
- 中文城市名转换：通过和风城市搜索 API 转换为经纬度
- 天气提醒联动："如果下雨就提醒我带伞"的条件判断
- 城市搜索缓存：ConcurrentHashMap 缓存城市转换结果

#### 2.1.6 RAG 知识库与长期记忆

- **私有记忆存储**：用户告诉系统的事实信息（如"我是大三学生"）自动存入 Chroma 向量库
- **语义检索**：用户询问个人信息时，通过向量相似度检索相关记忆
- **记忆管理**：支持更新、删除、查看所有记忆
- **分类管理**：PERSONAL_INFO / ACTIVITY / EVENT / PLAN / EXAM_SCHEDULE / DAILY_ROUTINE 等 12 个分类
- **公共知识库**：系统使用手册等公共文档的存储和检索
- **Embedding 模型**：本地 Ollama 运行 qwen3-embedding:4b 模型，无需外部 API

#### 2.1.7 多模型协同

- **DeepSeek（对话模型）**：负责 AI 对话、意图识别、工具调用推理、修改意图解析、天气建议生成
- **通义千问（识别模型）**：负责课表 Excel 结构化识别，返回课程 JSON
- **模型隔离**：DeepSeek 通过 Spring AI ChatModel 接口调用；通义千问通过 DashScope SDK 直接调用
- **API Key 管理**：DeepSeek 通过环境变量 `DEEPSEEK_API_KEY` 配置；通义千问通过 `dashscope.api.key` 系统属性配置

#### 2.1.8 日历视图

- 月历展示提醒事项
- 按日期筛选提醒
- 可视化提醒密度

### 2.2 非功能需求

| 需求 | 指标 |
|------|------|
| 响应时间 | AI 对话响应 < 5 秒 |
| 并发能力 | 支持 100+ 并发用户 |
| 可靠性 | 提醒推送不丢失 |
| 时区一致性 | 全系统 Asia/Shanghai |
| 安全性 | JWT 认证，接口鉴权 |

### 3.2 Agent 架构（ReAct 模式）

系统采用 ReAct（Reasoning + Acting）模式实现 AI 智能体调度：

```
用户输入
    │
    ▼
┌─────────────┐
│ AgentService │ ← MAX_ITERATIONS=5, MAX_TOOL_CALLS=5
└──────┬──────┘
       │
       ▼
┌─────────────────────┐
│ 1. 思考 (Reasoning)  │ ← LLM 分析用户意图，决定是否调用工具
└──────┬──────────────┘
       │ 需要工具？
       ▼
┌─────────────────────┐     否    ┌──────────────┐
│ 2. 行动 (Acting)     │─────────→│ 直接回复用户  │
│    调用 ToolRegistry  │          └──────────────┘
└──────┬──────────────┘
       │ 工具返回结果
       ▼
┌─────────────────────┐
│ 3. 观察 (Observation)│ ← 将工具返回结果注入对话上下文
└──────┬──────────────┘
       │
       ▼
   回到步骤 1（直到完成或达到最大迭代）
```

## 4. 核心技术实现细节

### 4.1 Agent 智能体调度（DeepSeek 驱动）

**文件**: `agent/AgentService.java` + `service/LLMService.java`

系统实现了基于 ReAct 模式的智能体调度器，由 DeepSeek 大模型驱动推理：

#### 双模型架构

```
┌──────────────────────────────────────────────────┐
│                  用户输入                          │
└──────────────────────┬───────────────────────────┘
                       │
         ┌─────────────┴──────────────┐
         │                            │
         ▼                            ▼
┌─────────────────┐         ┌─────────────────────┐
│  DeepSeek 对话   │         │  通义千问 识别       │
│  (Spring AI)    │         │  (DashScope SDK)    │
│                 │         │                     │
│ · 意图识别       │         │ · 课表结构识别       │
│ · 工具调用推理    │         │ · 课程信息提取       │
│ · 多轮对话       │         │ · 时间段推断         │
│ · 修改意图解析    │         │ · 学期周数推断       │
│ · 天气建议生成    │         │                     │
└─────────────────┘         └─────────────────────┘
```

- **DeepSeek 配置**：通过 `spring.ai.openai` 配置 `base-url: https://api.deepseek.com`，`model: deepseek-v4-flash`，利用 Spring AI 的 OpenAI 兼容接口
- **通义千问配置**：通过 `QwenConfig` 读取 `dashscope.api.key` 系统属性，`QwenRecognitionService` 使用 DashScope SDK 直接调用
- **LLMService** 注入 Spring AI 的 `ChatModel`（自动绑定 DeepSeek），统一提供 `parseReminder`、`chatWithTools`、`parseToolCalls`、`parseEditIntent`、`generateWeatherSuggestion` 等方法

#### ReAct 调度核心

- **迭代控制**：`MAX_ITERATIONS=5` 和 `MAX_TOOL_CALLS=5` 防止无限循环
- **工具注册**：`ToolRegistry` 管理所有可用工具（23 个工具：创建提醒、查询天气、RAG 存取、位置查询、经期管理等）
- **对话记忆**：`ConversationMemory` 维护多轮对话上下文（最多 10 条）
- **事件驱动**：通过 Spring Event 机制发布 `ReminderCreatedEvent`、`ReminderConfirmedEvent` 等
- **位置感知**：支持注入 GPS 坐标上下文

#### System Prompt 工程

`LLMService.buildSystemPromptWithTools()` 构建了超过 1200 行的 System Prompt，包含：
- 8 条最高优先级铁律（先调用工具再回复、禁止过程性语言、多任务依赖排序等）
- 23 个工具的详细说明和调用示例
- 条件判断规则（"如果下雨就提醒我"）
- 模糊时间解析规则（"等会" → +10分钟）
- 工具调用防重复规则
- RAG 工具使用说明（私有记忆 vs 公共知识）
- 回复风格要求（口语化、适当 emoji）

#### JSON 工具调用解析

`parseToolCalls` 方法支持三种格式的工具调用解析：
- 标准格式 `{"tool_call": {"name": "...", "arguments": {...}}}`
- OpenAI 格式 `{"function_call": {"name": "...", "arguments": "..."}}`
- 简化格式 `{"tool": "...", "arguments": {...}}`

解析容错机制：
- `fixJson`：修复 Markdown 代码块标记、缺失闭合括号、尾随逗号、未转义引号
- `extractAllTopLevelJsonObjects`：平衡括号扫描提取多个 JSON 对象（支持一次返回多个工具调用）
- `extractJsonFragment`：从混合文本中提取 JSON 片段

### 4.2 课表 AI 识别

**文件**: `service/QwenRecognitionService.java`

使用通义千问大模型识别 Excel 课表：

- **Prompt 设计**：结构化 Prompt 指导 AI 识别表格行列、合并连续节次
- **表格结构**：Excel 解析后用 `|` 分隔列，AI 明确识别表格边界
- **合并规则**：同一课程连续多节合并为一条（`sectionIndices: [1, 2]`）
- **课表检测**：`isScheduleTable()` 支持 `周一`~`周五`、`第1节`~`第10节` 等 38 个关键词
- **解析容错**：AI 返回的 JSON 可能包含 markdown 包裹，自动清理

### 4.3 时间推断与联动

**文件**: `index.html` (前端) + `service/ScheduleImportService.java` (后端)

#### 前端时间联动

用户在时间配置卡片中修改节次时间时，系统自动推断和联动：

- **课时推断**：从已填写的完整节次中取众数（`getMostCommon`）
- **自动填充**：修改开始时间时，自动用推断课时填充结束时间
- **向下联动**：修改某节后，自动更新后续未手动修改的节次
- **合法性校验**：`validateAllSlots` 确保节次时间不冲突
- **用户标记**：`_userFilled` 标记区分用户手动修改和系统自动填充

#### 后端时间生成

- **学期周数**：用户配置的 `totalWeeks` 覆盖课程自带的 weeks 列表
- **日期计算**：`semesterStart.plusWeeks(week - 1)` 计算每周日期
- **节次映射**：课程节次索引映射到时间段的开始/结束时间
- **单双周过滤**：支持 oddWeek（单周）/ evenWeek（双周）过滤

### 4.4 冲突检测算法

**文件**: `service/ConflictDetectionService.java`

#### 单点提醒冲突检测

```java
// 新提醒 [start, end] 与已有提醒 [oldStart, oldEnd] 重叠条件
// 单点提醒（endTime=null）使用 ±30分钟 窗口
if (newReminder.endTime == null) {
    // 检查 |newStart - oldStart| < 30分钟
}
```

#### 时间段提醒冲突检测

```java
// 时间段重叠检测：start < oldEnd AND end > oldStart
if (newStart.isBefore(oldEnd) && newEnd.isAfter(oldStart)) {
    // 冲突
}
```

- **检测时机**：创建确认会话时检测，而非最终创建时
- **检测范围**：仅包含 CONFIRMED 状态的提醒，排除待确认提醒
- **自排除**：修改提醒时排除自身 ID，避免自冲突

### 4.5 WebSocket 实时推送

**文件**: `config/WebSocketConfig.java` + `service/WebSocketPushService.java`

- **用户级定向推送**：`convertAndSendToUser` 推送到 `/user/queue/*`
- **握手认证**：`HandshakeHandler` 从 URL 查询参数读取 `user-id`
- **推送目标**：
  - `/queue/confirmations` - 确认卡片
  - `/queue/messages` - 普通消息和导入结果
- **批量导入优化**：`batchCreateSilently` 只推送一条汇总消息，避免逐条推送轰炸

### 4.6 确认卡片系统

**文件**: `dto/response/ConfirmationCardResponse.java`

确认卡片支持多种类型，通过 `type` 字段区分：

| 卡片类型 | 说明 | 触发场景 |
|----------|------|----------|
| `confirmation_card` | 冲突确认 | 创建提醒检测到冲突 |
| `success` | 创建成功 | 提醒创建成功 |
| `cancelled` | 已取消 | 用户取消创建 |
| `timeout` | 超时 | 确认会话超时 |
| `timeout_auto_create` | 超时自动创建 | 超时后自动创建 |
| `schedule_table_confirm` | 课表确认 | AI 识别课表后 |
| `time_config_card` | 时间配置 | 用户调整课表时间 |
| `schedule_preview` | 日程预览 | 生成日程后预览 |
| `manual_create_card` | 手动创建 | 手动输入课程 |

### 4.7 批量静默创建

**文件**: `service/ScheduleImportService.java`

课表导入场景的优化方案：

- **问题**：逐条创建提醒会触发 N 次确认会话和 N 次 WebSocket 推送
- **方案**：`batchCreateSilently` 直接 `reminderRepository.save()`，跳过确认流程
- **结果**：N 条日程 → 1 条汇总消息（"成功创建 N 条提醒"）
- **配置持久化**：用户修改的 `totalWeeks`、`semesterStartDate`、`timeSections` 保存到 `ScheduleImport` 实体，后续"直接创建"时读取用户配置而非默认值

### 4.8 天气服务集成

**文件**: `service/WeatherService.java` + `service/LocationService.java`

- **和风天气 API**：实时天气、空气质量、天气预报
- **中文城市名转换**：调用 `/geo/v2/city/lookup` 转换为经纬度
- **缓存机制**：`ConcurrentHashMap` 缓存城市转换结果
- **降级策略**：非城市地点降级使用用户默认城市；API 失败降级返回原城市名
- **条件判断**：`weather.text` 包含"雨"/"暴雨"/"大雨" → 判定为雨天；`temp > 35°C` → 高温；`temp < 5°C` → 低温

### 4.9 时区与时间处理

- **全局时区**：`@PostConstruct` 设置 JVM 默认时区为 `Asia/Shanghai`
- **DTO 序列化**：`LocalDateTime` 使用 `@JsonFormat(pattern = "yyyy-MM-dd HH:mm:ss", timezone = "Asia/Shanghai")`
- **时间工具类**：`TimeUtils` 统一处理时间操作，禁止直接使用 `LocalDateTime.now()`、`new Date()`

### 4.10 RAG 知识库与长期记忆

**文件**: `service/RagService.java` + `config/ChromaConfig.java`

系统基于 Chroma 向量数据库实现 RAG（检索增强生成）长期记忆：

#### 架构设计

```
用户输入事实信息（如"我是大三学生"）
    │
    ▼
add_private_memory 工具
    │
    ▼
RagService → Ollama Embedding（qwen3-embedding:4b）
    │  将文本转为向量
    ▼
Chroma 向量数据库存储
    │  collection: public_knowledge
    │  按用户 ID 和分类（category）隔离
    ▼
后续用户询问"我的专业是什么？"
    │
    ▼
retrieve_private_knowledge 工具
    │
    ▼
RagService → 向量相似度检索
    │  返回 top-K 相关记忆
    ▼
DeepSeek 综合记忆 + 上下文 → 自然语言回复
```

#### 双重知识库

| 知识库 | 用途 | 工具 |
|--------|------|------|
| 私有记忆 | 用户个人事实信息（专业、习惯、偏好等） | `add_private_memory` / `retrieve_private_knowledge` / `update_private_memory` / `delete_private_memory` / `get_all_private_memories` |
| 公共知识 | 系统使用手册等公共文档 | `retrieve_public_knowledge` |

#### 记忆分类体系

12 个预定义分类：PERSONAL_INFO（个人信息）、ACTIVITY（活动事务）、EVENT（重要日期）、PLAN（长期目标）、EXAM_SCHEDULE（考试安排）、DAILY_ROUTINE（日常作息）、HEALTH_CONDITION（健康状况）、DIET_PREFERENCE（饮食偏好）、HABIT（个人习惯）、INTEREST（兴趣爱好）、LANGUAGE_STYLE（语言风格）、OTHER

#### Embedding 方案

- **本地部署**：Ollama 运行 `qwen3-embedding:4b`，无需外部 API
- **配置**：`spring.ai.ollama.base-url: http://localhost:11434`
- **向量存储**：Chroma `http://localhost:8000`，collection `public_knowledge`

### 4.11 定时任务与推送系统

**文件**: `service/SchedulerService.java` + `service/PushService.java` + `service/RecurringReminderService.java`

#### 提醒推送调度

`SchedulerService` 使用 `@Scheduled` 定时任务扫描到期提醒：

```
@Scheduled(fixedRate = 60000)  // 每分钟扫描一次
扫描 status=PENDING 且 remindTime <= now 的提醒
    │
    ├── WebSocket 推送（在线用户）→ /user/queue/messages
    ├── 记录推送日志（PushLog）
    └── 更新提醒状态（PENDING → EXECUTED）
```

#### 循环提醒

`RecurringReminderService` 支持三种重复类型：

| 类型 | 说明 | 实例生成 |
|------|------|----------|
| DAILY | 每日重复 | 每天指定时间生成提醒实例 |
| WEEKLY | 每周重复 | 每周指定星期几生成提醒实例 |
| MONTHLY | 每月重复 | 每月指定日期生成提醒实例 |

- **RecurringReminder**：循环提醒模板（标题、时间、重复类型、起止日期）
- **RecurringInstance**：每次循环生成的具体提醒实例

#### 推送渠道

`PushChannel` 枚举定义推送渠道，`PushService` 统一管理推送逻辑，`PushLog` 记录每次推送结果。

## 6. 优化方案

### 6.1 批量创建优化

**问题**：课表导入 24 条日程 → 24 条 WebSocket 消息轰炸用户

**方案**：新增 `batchCreateSilently` 方法，直接写入数据库，仅推送一条汇总消息

**效果**：24 条消息 → 1 条汇总消息

### 6.2 课表识别优化

**问题**：AI 将 Excel 课表解析为 24 个独立日程（逐单元格平铺）

**方案**：
- Excel 解析改用 `|` 分隔列，表格结构更清晰
- Prompt 增加合并规则：连续节次同课程合并为一条
- `isScheduleTable` 关键词扩展至 38 个，匹配阈值降至 2

**效果**：24 条 → 3 条课程（合并连续节次）

### 6.3 时间配置持久化

**问题**：用户修改的日期、周数、时间在"直接创建"时不生效

**方案**：
- `ScheduleImport` 实体新增 `totalWeeks`、`semesterStartDate` 字段
- `generateScheduleFromImport` 保存用户配置到实体
- `createRemindersFromCache` 优先读取 importRecord 中的配置
- 用户修改的 timeSections 写回缓存

**效果**：用户配置的时间、日期、周数全部生效

### 6.4 冲突检测优化

**问题**：冲突卡片操作复杂，用户需要逐条处理

**方案**：
- 全选/反选功能：一键选中所有冲突项
- 批量覆盖：勾选后批量删除冲突提醒
- 单个覆盖：每个冲突项独立覆盖按钮
- 卡片状态缓存：`originalConfirmationCard` 缓存原始数据，取消修改时恢复

### 6.5 前端交互优化

- **无弹窗交互**：所有操作通过卡片完成，禁止 `alert`/`prompt`
- **加载状态反馈**：按钮点击后显示加载文字并禁用
- **滚动条样式**：自定义 4px 宽度滚动条，主题色滑块
